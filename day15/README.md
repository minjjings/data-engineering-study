## 1장. 개념 이해하기

지연 도착은 데이터의 거래일보다 훨씬 나중에 수집되는 상황이다. 거래일 최대값만 기억하면 과거 날짜 수정이 누락될 수 있다. 최근 구간을 겹쳐 다시 읽고 업무 키로 UPSERT하면 정해진 범위의 지연을 흡수할 수 있다.

겹치는 구간보다 오래된 수정까지 자동 해결되지는 않는다. 그래서 증분 처리와 함께 특정 날짜 재처리·전체 대사 경로를 남긴다. 처리 위치를 유지하는 규칙과 어느 범위까지 복구를 보장하는지 명확히 설명해야 한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```sql
WITH incoming(id, trade_date, collected_at) AS (
    VALUES (6, DATE '2026-10-25', TIMESTAMP '2026-10-29 09:00:00'),
           (7, DATE '2026-10-28', TIMESTAMP '2026-10-29 09:01:00')
)
SELECT *, trade_date > DATE '2026-10-27' AS by_trade_date,
          id > 5 AS by_arrival_id
FROM incoming ORDER BY id;
```

**예상 결과와 확인 기준:** 거래일 조건은 id 6을 놓치지만 도착 id 조건은 두 행을 선택한다. 이것만으로 동시 커밋 상황까지 안전함을 증명한 것은 아니다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. 정상 신규·같은 입력·과거 거래일 수정·적재 중 실패 4개 시나리오의 예상 상태를 작성한다.
2. Day 14의 영구 테이블로 4개 시나리오를 실행해 최종 키·가격·상태를 비교한다.
3. 3주 리뷰에 키 설계·트랜잭션·인덱스·지연 도착과 단일 작업 가정을 정리한다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day15/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

SQL 실행 위치를 확인한다. 일반 PostgreSQL SQL은 psql에서, Athena SQL은 Athena에서, Jinja가 있는 모델 SQL은 dbt 모델 파일에서 실행한다. TEMP 테이블은 생성한 연결에서만 보인다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
