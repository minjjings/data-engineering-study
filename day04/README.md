## 1장. 개념 이해하기

매번 모든 원본을 읽는 전체 적재와 달리 증분 적재는 처리할 범위를 제한한다. Watermark는 어디까지 성공했는지 저장하는 표시다. 거래일은 데이터의 의미상 날짜이고 수집 순서는 시스템에 들어온 순서이므로 같은 기준이 아니다.

오늘은 증가하는 id를 단순한 수집 위치로 사용한다. 실제 시스템에서는 늦게 커밋되는 행을 id만으로 놓칠 수 있어 변경 로그나 겹치는 조회 범위가 필요하다. 상태를 먼저 전진시키고 적재가 실패하면 데이터가 누락되므로 상태 갱신은 적재 성공과 연결해야 한다.

## 2장. 실습 준비

Day 1·2의 Python과 PostgreSQL 환경을 사용한다. 저장소 최상위 PowerShell에서 `docker compose up -d` 후 `docker exec -it de-postgres psql -U de_user -d market_db`로 접속한다. SQL 블록은 psql에서 실행한다. 원본 5건을 유지하고, 예제의 임시 테이블은 현재 접속에서만 사용한다.

이전 학습일의 과제를 아직 구현하지 않았다면 해당 교재에서 먼저 준비한다. 문서 안의 파일명은 앞으로 작성할 산출물을 포함한다. 첫 사용 환경은 이번 주 첫 교재인 [Day 1](../day01/README.md)의 준비 항목도 확인한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```sql
WITH state AS (SELECT 3::bigint AS last_id)
SELECT p.id, p.symbol, p.trade_date, p.close_price
FROM raw_market_prices AS p CROSS JOIN state AS s
WHERE p.id > s.last_id
ORDER BY p.id;
```

**예상 결과와 확인 기준:** 최초 원본 id가 1~5이면 id 4·5만 조회된다. 두 행은 새로 수집한 행이지만 가격은 NULL·N/A이므로 품질 통과와는 별개다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. last_id를 0, 3, 5로 바꾸고 각각 5건, 2건, 0건을 확인한다.
2. 거래일이 과거인 데이터가 오늘 도착하는 경우 거래일 Watermark가 놓치는 상황을 표로 만든다.
3. 조회 → 검증 → 저장 → 상태 갱신 순서를 적고 저장 실패 시 상태를 어떻게 유지할지 설명한다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day04/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

SQL 실행 위치를 확인한다. 일반 PostgreSQL SQL은 psql에서, Athena SQL은 Athena에서, Jinja가 있는 모델 SQL은 dbt 모델 파일에서 실행한다. TEMP 테이블은 생성한 연결에서만 보인다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
