## 1장. 개념 이해하기

인덱스는 조건에 맞는 행을 빠르게 찾기 위한 별도 자료구조다. 읽기를 줄일 수 있지만 디스크와 쓰기 비용을 추가한다. 작은 표에서는 전체를 읽는 순차 스캔이 더 저렴할 수 있으므로 인덱스 사용 여부 자체를 성능 목표로 삼지 않는다.

EXPLAIN은 예상 계획을 보여주고 EXPLAIN ANALYZE는 실제 쿼리를 실행하며 측정한다. 변경 SQL에 ANALYZE를 붙이면 실제 변경도 일어나므로 오늘은 SELECT만 측정한다. 통계 갱신 후 같은 조건으로 비교한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```sql
CREATE TEMP TABLE lab_lookup AS
SELECT n AS id, 'symbol-' || n AS symbol
FROM generate_series(1, 50000) AS n;
ANALYZE lab_lookup;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_lookup WHERE id = 42000;
CREATE INDEX ON lab_lookup(id);
ANALYZE lab_lookup;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM lab_lookup WHERE id = 42000;
```

**예상 결과와 확인 기준:** 두 SELECT는 모두 같은 1건을 반환한다. 인덱스 전후 scan 방식·읽은 블록·실행 시간을 기록하되 특정 속도 배수를 정답으로 가정하지 않는다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. 필터를 id > 0으로 바꾸어 많은 행을 반환할 때 계획을 비교한다.
2. 복합 키 symbol·trade_date 인덱스가 어떤 조건에 유리할지 적는다.
3. 한 번의 시간보다 여러 실행의 편차와 캐시 영향을 포함해 비교를 기록한다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day13/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

SQL 실행 위치를 확인한다. 일반 PostgreSQL SQL은 psql에서, Athena SQL은 Athena에서, Jinja가 있는 모델 SQL은 dbt 모델 파일에서 실행한다. TEMP 테이블은 생성한 연결에서만 보인다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
