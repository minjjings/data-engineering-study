## 1장. 개념 이해하기

CTE는 긴 SQL을 이름 있는 중간 결과로 나누는 표현이다. 원본 조회, 형식 확인, 정상 가격 필터를 나누면 어디에서 행이 줄었는지 설명하기 쉽다. CTE를 쓴다고 결과가 영구 저장되지는 않는다.

CASE는 조건을 만족하는 값에만 변환을 적용한다. 오늘의 정규식은 부호 없는 정수·소수만 허용한다. 음수·지수 표기·공백을 허용할지는 별도 계약이며 숫자처럼 보인다는 사실만으로 양수 가격인 것은 아니다.

## 2장. 실습 준비

Day 2의 PostgreSQL에 접속한다. 아래 `WITH prices ... VALUES` 예제는 원본 테이블과 독립적인 가상 가격 4건이다. CTE는 해당 문장에서만 존재하므로 SQL 블록 전체를 실행한다. 직접 작성할 쿼리는 `sql/week02/`에 저장한다.

이전 학습일의 과제를 아직 구현하지 않았다면 해당 교재에서 먼저 준비한다. 문서 안의 파일명은 앞으로 작성할 산출물을 포함한다. 첫 사용 환경은 이번 주 첫 교재인 [Day 6](../day06/README.md)의 준비 항목도 확인한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```sql
WITH raw(value) AS (
    VALUES ('620.50'), ('N/A'), (NULL), ('0'), ('-1'), (' 621 ')
), parsed AS (
    SELECT value, CASE WHEN value ~ '^[0-9]+([.][0-9]+)?$'
        THEN value::numeric END AS price FROM raw
)
SELECT value, price, CASE WHEN price > 0 THEN 'valid'
    ELSE 'rejected' END AS status FROM parsed;
```

**예상 결과와 확인 기준:** 6건 중 정상은 620.50 한 건이다. 0은 숫자 변환에는 성공하지만 양수 규칙을 통과하지 못한다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. btrim으로 앞뒤 공백을 허용하는 규칙을 만들고 정상 건수가 2건이 되는지 확인한다.
2. 실패 이유를 missing, invalid_format, non_positive로 구분한다.
3. 형식 검사와 CAST를 단순 AND로 연결하는 방식이 안전하지 않은 이유를 적는다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day08/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

SQL 실행 위치를 확인한다. 일반 PostgreSQL SQL은 psql에서, Athena SQL은 Athena에서, Jinja가 있는 모델 SQL은 dbt 모델 파일에서 실행한다. TEMP 테이블은 생성한 연결에서만 보인다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
