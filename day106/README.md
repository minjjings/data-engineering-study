# Day 106. 검증 범위와 의존성 고정

**22주 차 · 주간 1일차 | 약 90~120분**

[전체 계획](../README.md) · [120일 목차](../README.md#day-index) · [← Day 105](../day105/README.md) · [Day 107 →](../day107/README.md)

이번 주에는 **테스트·CI/CD와 재현 가능한 환경** 내용을 다룬다. 오늘은 단위·통합·데이터 검사를 목적에 맞게 나눈다.

> 미리 작성한 교재다. 아래 예제·예상 결과는 학습 기준이며 실행을 완료했다는 뜻은 아니다. 과제에서 요구하는 코드·설정·결과는 직접 작성한다. 시장 가격은 가상 데이터다.

## 오늘의 학습 목표

- 단위·통합·데이터 검사를 목적에 맞게 나눈다.
- 예제의 입력과 결과를 비교하고 처리 기준을 자기 말로 설명한다.
- 직접 작성한 과제와 실행 근거를 남긴다.

| 순서 | 할 일 | 예상 시간 |
| --- | --- | --- |
| 1 | 개념과 준비 항목 확인 | 20분 |
| 2 | 예제 실행·입출력 확인 | 25~35분 |

## 1장. 개념 이해하기

단위 검사는 정제 규칙, 통합 검사는 파일·DB 경계, 데이터 검사는 실제 결과의 품질을 확인한다. 모든 도구를 매번 실행하기보다 변경 영향에 맞게 핵심 경로를 고른다. 의존성은 전용 환경에서 기록해 불필요한 패키지가 섞이지 않게 한다.

## 2장. 실습 준비

4~5주 src와 tests, dbt 프로젝트가 준비되어 있어야 한다. 루트 requirements.txt에 실제 필요한 패키지와 버전을 정리한다. CI는 GitHub Actions의 독립 PostgreSQL17 서비스를 사용하고 로컬 실습DB·AWS 계정에 연결하지 않는다. workflow는 작성·로컬 확인 후 사용자가 push했을 때 원격 실행 결과를 확인한다.

이전 학습일의 과제를 아직 구현하지 않았다면 해당 교재에서 먼저 준비한다. 문서 안의 파일명은 앞으로 작성할 산출물을 포함한다. 첫 사용 환경은 이번 주 첫 교재인 [Day 106](../day106/README.md)의 준비 항목도 확인한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests
.\.venv\Scripts\python.exe -m pip freeze
docker compose config --quiet
```

**예상 결과와 확인 기준:** 정의한 테스트가 실제로 발견되어 실행되는지 개수를 확인한다. Ran 0 tests는 핵심 동작을 검증한 성공으로 보지 않는다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. 정제·DB 롤백·멱등UPSERT 중 핵심 규칙의 검사를 정리한다.
2. 사용 패키지 버전과Python버전을 requirements·실행 안내에 남긴다.
3. 코드 오류와 외부 환경 미준비를 구분하는 검증 표를 작성한다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day106/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

명령은 저장소 루트의 PowerShell에서 실행한다. 환경변수와 컨테이너 상태를 먼저 확인하고 오류 전문을 기록한다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
