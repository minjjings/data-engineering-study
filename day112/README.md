# Day 112. 아키텍처·스키마·데이터 계보

**23주 차 · 주간 2일차 | 약 90~120분**

이번 주에는 **통합 프로젝트 최소 배치와 스트리밍 확장** 내용을 다룬다. 오늘은 각 단계의 입력·출력·책임을 명시한다.

> 미리 작성한 교재다. 아래 예제·예상 결과는 학습 기준이며 실행을 완료했다는 뜻은 아니다. 과제에서 요구하는 코드·설정·결과는 직접 작성한다. 시장 가격은 가상 데이터다.

## 오늘의 학습 목표

- 각 단계의 입력·출력·책임을 명시한다.
- 예제의 입력과 결과를 비교하고 처리 기준을 자기 말로 설명한다.
- 직접 작성한 과제와 실행 근거를 남긴다.

| 순서 | 할 일 | 예상 시간 |
| --- | --- | --- |
| 1 | 개념과 준비 항목 확인 | 20분 |
| 2 | 예제 실행·입출력 확인 | 25~35분 |

## 1장. 개념 이해하기

아키텍처는 그림뿐 아니라 데이터 계약·실패 경계·저장 위치를 포함한다. 연결마다 형식·grain·실행 주체를 적으면 중복 책임을 찾기 쉽다. Glue의 Catalog 역할과 관리형 변환 실험도 구분한다.

## 2장. 실습 준비

기존 src·Spark·DW·dbt·Airflow를 사용한다. 설계는 docs/project에 모으고 가상 시장 가격 예제를 확장한다. 최소 배치 경로부터 검증하고 CDC는 별도 대상 표의 확장 경로로 둔다. 각 day 예제의 설계를 실제 코드로 연결하는 단계다.

이전 학습일의 과제를 아직 구현하지 않았다면 해당 교재에서 먼저 준비한다. 문서 안의 파일명은 앞으로 작성할 산출물을 포함한다. 첫 사용 환경은 이번 주 첫 교재인 [Day 111](../day111/README.md)의 준비 항목도 확인한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```text
수집 CLI → S3 Raw (JSONL, ingest_date)
Spark → S3 curated (Parquet, trade_date, batch_id)
검증 배치 → PostgreSQL DW (UPSERT)
dbt → 분석 mart → 품질 통과 → 공개
Glue Catalog + Athena → S3 결과 대사
Airflow → 구간·순서·상태 관리
```

**예상 결과와 확인 기준:** 모든 연결에 실제 경로·키·버전·실패 시 행동을 대응시킨다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. ERD와 흐름을 작성하고 원본·정제·마트의 grain을 적는다.
2. 컬럼명·가격 타입·UTC 시각·파티션·batch_id를 통일한다.
3. Spark·Glue의 변환 책임과 중복 구현 여부를 결정한다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day112/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

설계·검증 시나리오 예제는 실행 결과와 대응시켜 읽는다. 실행 명령으로 입력하지 않고 본인이 구현한 코드·로그·결과와 대응시킨다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
