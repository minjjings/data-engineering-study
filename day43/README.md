## 1장. 개념 이해하기

full-refresh는 기존 증분 표를 다시 만든다. 증분 필터·지연 데이터 규칙이 틀리면 전체 재구축 결과와 달라질 수 있다. 비교 전에 기존 결과를 복사해야 차이를 증명할 수 있고 실제 운영 표를 임의로 재생성하지 않는다.

## 2장. 실습 준비

기존 dbt 프로젝트를 사용하며 `seeds/incremental_input.csv`에 symbol,trade_date,close_price 헤더와 QQQ,2026-10-26,620.50 및 SPY,2026-10-26,680.20 두 행을 준비한다. Day 41~44에서는 이 seed를 바꾸며 실험한다. Airflow 연동은 Worker 이미지 안에도 같은 dbt 어댑터·프로젝트·profile을 배치해야 한다.

이전 학습일의 과제를 아직 구현하지 않았다면 해당 교재에서 먼저 준비한다. 문서 안의 파일명은 앞으로 작성할 산출물을 포함한다. 첫 사용 환경은 이번 주 첫 교재인 [Day 41](../day41/README.md)의 준비 항목도 확인한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```sql
-- psql: dbt full-refresh 전에 증분 결과를 보관한다.
CREATE TABLE analytics.lab_incremental_before AS
SELECT * FROM analytics.fct_prices_incremental;
-- 재구축 후 양방향 EXCEPT로 비교한다.
SELECT * FROM analytics.lab_incremental_before
EXCEPT
SELECT * FROM analytics.fct_prices_incremental;
```

**예상 결과와 확인 기준:** 정상 범위의 데이터만 있으면 양방향 차이가 0건이다. 범위 밖 수정 실험이 있으면 차이가 나타날 수 있다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. 비교용 표를 만든 뒤 dbt run --full-refresh --select fct_prices_incremental을 실행한다.
2. 양방향 EXCEPT를 모두 수행해 누락과 초과를 구분한다.
3. 어떤 상황에서 전체 재구축을 수행할지 비용·복구 시간을 포함해 적는다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day43/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

SQL 실행 위치를 확인한다. 일반 PostgreSQL SQL은 psql에서, Athena SQL은 Athena에서, Jinja가 있는 모델 SQL은 dbt 모델 파일에서 실행한다. TEMP 테이블은 생성한 연결에서만 보인다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
