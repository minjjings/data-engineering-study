## 1장. 데이터 엔지니어는 어떤 일을 할까?

### 데이터를 가져오기만 하면 끝일까?

미국 ETF인 QQQ의 가격을 매일 가져온다고 생각해보자. ETF는 여러 자산을 묶어서 주식처럼 사고팔 수 있게 만든 상품이다.

Python으로 API에 요청하면 다음과 같은 데이터를 받을 수 있다. API는 **다른 프로그램에 데이터를 요청할 수 있는 창구**라고 생각하면 된다.

```json
{
  "symbol": "QQQ",
  "date": "2026-10-26",
  "close": 620.50,
  "volume": 45000000
}
```

**이 수업의 가격과 거래량은 모두 학습용 가상 데이터이며 실제 QQQ 시세가 아니다.**

| 항목 | 뜻 |
| --- | --- |
| `symbol` | 종목을 나타내는 코드 |
| `date` | 데이터의 기준 날짜 |
| `close` | 그날 거래가 끝났을 때의 가격인 종가 |
| `volume` | 그날 거래된 수량인 거래량 |

데이터를 한 번 가져오는 코드는 짧을 수 있다. 하지만 매일 반복해서 가져오다 보면 다음 문제가 생길 수 있다.

| 생길 수 있는 문제 | 생각해야 할 일 |
| --- | --- |
| API가 응답하지 않는다 | 언제 다시 시도할까? |
| 같은 날짜의 데이터를 두 번 가져왔다 | 두 번 저장되지 않게 하려면 어떻게 할까? |
| 가격이 `null`로 들어왔다 | 가격이 없는 데이터를 어떻게 처리할까? |
| 데이터 형식이 바뀌었다 | 바뀐 형식을 알아차릴 수 있을까? |
| 수집에는 성공했지만 데이터베이스 저장에 실패했다 | 어디서부터 다시 실행해야 할까? |

데이터 엔지니어는 이런 문제를 고려해 **데이터가 꾸준히 들어오고, 올바르게 저장되고, 문제가 생겨도 다시 처리할 수 있도록 시스템을 만드는 사람**이다.

### 데이터 파이프라인이 필요한 이유

데이터 파이프라인은 **데이터를 가져와서 → 필요한 처리를 하고 → 저장하는 흐름**이다.

이 흐름을 프로그램으로 만들어두면 매번 사람이 파일을 열어 정리할 필요가 줄어든다. 어느 단계에서 실패했는지 확인하고 다시 실행할 수 있도록 구성할 수도 있다. 단, 파이프라인을 만들었다고 오류 처리가 자동으로 해결되는 것은 아니다. 확인 규칙과 재시도 방법도 함께 정해야 한다.

### 수집 성공과 데이터 품질은 다르다

“API에서 응답을 받았다”는 것은 데이터를 가져왔다는 뜻이다. **가져온 내용이 모두 올바르다는 뜻은 아니다.**

응답 안에 가격이 빠져 있거나, 같은 데이터가 반복되거나, 날짜가 잘못되어 있을 수 있다. 이렇게 데이터가 사용하기에 적절한지 확인하는 것이 데이터 품질 검사다.

## 2장. ETL과 ELT는 무엇이 다를까?

### 먼저 세 단어 이해하기

| 용어 | 쉬운 뜻 | 예시 |
| --- | --- | --- |
| Extract · 추출 | 데이터를 가져오기 | API에서 가격 가져오기 |
| Transform · 변환 | 사용할 수 있게 바꾸기 | 가격을 숫자로 바꾸고 중복 제거하기 |
| Load · 적재 | 사용할 곳에 저장하기 | 데이터베이스에 저장하기 |

ETL과 ELT는 이 세 작업을 **어떤 순서로 하는지**가 다르다. 특히 데이터를 바꾸는 작업이 어디에서 일어나는지 보자.

### ETL: 정리한 뒤 저장하기

```text
API에서 가져오기 → Python에서 정리하기 → PostgreSQL에 저장하기
      E                   T                       L
```

PostgreSQL은 데이터를 표 형태로 저장하고 SQL로 조회할 수 있는 데이터베이스다. ETL에서는 Python 같은 프로그램이 데이터를 정리한 뒤, 그 결과를 데이터베이스에 넣는다.

### ELT: 먼저 저장하고 나중에 정리하기

```text
API에서 가져오기 → PostgreSQL에 원본 저장하기 → SQL이나 dbt로 정리하기
      E                        L                         T
```

ELT에서는 원본을 먼저 데이터베이스 등에 넣고, 그 안의 데이터를 SQL 등으로 정리한다. SQL은 데이터베이스의 데이터를 조회하고 다룰 때 쓰는 언어다.

실제 시스템에서는 두 방식이 섞이기도 한다. 원본을 저장하기 전에 꼭 필요한 검사만 하고, 나머지 정리는 저장한 뒤에 할 수도 있다.

### 같은 데이터를 두 방식으로 처리해 보기

다음 데이터를 받았다고 해보자.

| symbol | date | close |
| --- | --- | --- |
| QQQ | 2026-10-26 | `"620.50"` |
| SPY | 2026-10-26 | `"680.20"` |
| QQQ | 2026-10-26 | `"620.50"` |

QQQ가 같은 날짜에 두 번 들어와 있다. 가격도 숫자가 아니라 `"620.50"`이라는 문자열, 즉 글자로 표현되어 있다.

문자열로 받은 것 자체가 항상 오류는 아니다. 다만 숫자 계산에 쓰려면 알맞은 숫자 형식으로 바꾸어야 한다.

| 방식 | 처리 방법 |
| --- | --- |
| ETL | Python에서 가격을 숫자로 바꾸고 중복을 제거한 뒤 데이터베이스에 저장 |
| ELT | 원본을 먼저 데이터베이스에 저장하고 SQL이나 dbt로 가격 변환과 중복 제거 |

### Raw 데이터와 정제된 데이터

**Raw 데이터는 처음 받은 상태의 데이터**, **정제된 데이터는 정해둔 규칙에 따라 정리한 데이터**다. 여기서 정제는 “사용하기 좋게 정리한다”는 뜻이다.

| 구분 | Raw 데이터 | 정제된 데이터 |
| --- | --- | --- |
| 담긴 내용 | 받은 데이터를 그대로 보관 | 검사와 정리를 통과한 데이터 |
| 중복·빈 가격 | 포함될 수 있음 | 정해둔 규칙에 따라 처리 |
| 보관 목적 | 처음 상태 확인과 재처리 | 조회·계산·분석에 사용 |
| 오늘의 파일 | `raw.json` | `clean.json` |

원본을 보관하면 정리 규칙을 잘못 만들었거나 나중에 바꾸고 싶을 때 처음 데이터부터 다시 처리할 수 있다.

### dbt는 어디에서 쓸까?

dbt는 주로 **ELT의 T, 즉 이미 저장된 데이터를 변환하는 단계**에서 사용한다. SQL로 변환 규칙을 작성하고, 어떤 결과를 먼저 만들어야 하는지 작업 사이의 순서도 관리할 수 있다. [dbt 모델 공식 문서](https://docs.getdbt.com/docs/build/models)

예를 들어 원본 데이터가 PostgreSQL의 `raw_market_prices`라는 표에 이미 저장되어 있다면 다음 SQL로 가격을 숫자로 바꿀 수 있다. 이 표는 오늘 실습에서는 만들지 않으며, 아래 코드는 개념을 이해하기 위한 예시다.

```sql
SELECT
    symbol,
    CAST(close AS NUMERIC) AS close_price
FROM raw_market_prices
WHERE close IS NOT NULL;
```

- `FROM`: 어느 표에서 가져올지 정한다.
- `WHERE close IS NOT NULL`: 가격이 비어 있지 않은 행만 고른다.
- `CAST(close AS NUMERIC)`: 가격을 숫자 형식으로 바꾼다.

**이 SQL은 중복을 제거하지 않는다.** 또 `"abc"`처럼 숫자로 바꿀 수 없는 문자열이 있으면 실패할 수 있다. 모든 품질 문제를 해결하는 쿼리는 아니다.

dbt에서는 데이터 확인 규칙도 선언할 수 있다.

| 검사 이름 | 확인하는 내용 |
| --- | --- |
| `not_null` | 값이 비어 있지 않은가? |
| `unique` | 같은 값이 중복되어 있지 않은가? |
| `relationships` | 다른 표에 있어야 할 연결 대상이 실제로 존재하는가? |

이 검사는 문제를 찾아주는 기능이며, 잘못된 데이터를 자동으로 고쳐주는 기능은 아니다. [dbt 데이터 테스트 공식 문서](https://docs.getdbt.com/docs/build/data-tests)

데이터와 변환 규칙에 설명을 붙여 문서로 남기는 기능도 제공한다. [dbt 문서화 공식 문서](https://docs.getdbt.com/docs/build/documentation)

### Airflow와 dbt의 역할 비교하기

| 도구 | 주요 역할 | 예시 |
| --- | --- | --- |
| Airflow | 여러 작업을 언제, 어떤 순서로 실행할지 관리하고 실행 상태 확인 | 매일 수집 → 저장 → 변환 작업을 순서대로 실행 |
| dbt | 저장된 데이터를 변환하고 결과를 검사 | 가격 형식 바꾸기, 중복 제거 규칙 작성, 빈 값 검사 |

Airflow는 전체 작업의 진행을 관리하고, dbt는 그중 데이터 변환과 검증에 쓰인다고 생각하면 된다. [Airflow 공식 소개](https://airflow.apache.org/docs/apache-airflow/stable/)

오늘은 두 도구를 설치하지 않는다. 우선 역할만 이해하고 Python으로 작은 흐름을 직접 만들어본다.

## 3장. 첫 번째 Python 실습

### 실습 1 — 원본 데이터 저장 및 정제

**난이도: 기초 | Python 3 사용 | 클라우드와 추가 패키지 설치 불필요**

오늘 실습의 목표는 세 가지다.

1. API에서 받았다고 가정한 데이터를 JSON 파일로 저장한다.
2. 중복 데이터와 잘못된 가격을 걸러낸다.
3. 정리한 결과를 별도 파일로 저장한다.

JSON은 데이터를 저장하거나 프로그램 사이에서 주고받을 때 쓰는 텍스트 형식이다.

### Step 1. 프로젝트 폴더 확인하기

현재 프로젝트에는 다음 파일이 준비되어 있다. 처음부터 따라 한다면 같은 구조로 폴더와 `pipeline.py`를 만든다. `data` 폴더는 코드가 없으면 만들어준다.

```text
 data-engineering-study/
 └── day01/
     ├── README.md
     ├── pipeline.py
     └── data/
```

### Step 2. Python 코드 실행하기

[pipeline.py](./pipeline.py)의 전체 코드는 다음과 같다. 실제 API를 호출하는 대신 `raw_data`에 미리 적어둔 데이터를 사용한다. 이번 실습에서는 종목, 날짜, 가격만 다룬다.

```python
import json
from pathlib import Path
from decimal import Decimal, InvalidOperation

data_dir = Path(__file__).parent / "data"
data_dir.mkdir(exist_ok=True)

# API에서 수집했다고 가정한 데이터
raw_data = [
    {"symbol": "QQQ", "date": "2026-10-26", "close": "620.50"},
    {"symbol": "SPY", "date": "2026-10-26", "close": "680.20"},
    {"symbol": "QQQ", "date": "2026-10-26", "close": "620.50"},
    {"symbol": "SPY", "date": "2026-10-27", "close": None},
]

# 1. Raw 데이터 보존
with open(data_dir / "raw.json", "w", encoding="utf-8") as f:
    json.dump(raw_data, f, ensure_ascii=False, indent=2)

# 2. 유효성 검사와 중복 제거
cleaned = []
seen = set()
invalid_count = 0

for row in raw_data:
    key = (row["symbol"], row["date"])

    if key in seen:
        continue

    try:
        price = Decimal(str(row["close"]))
        if not price.is_finite() or price <= 0:
            raise ValueError("Invalid price")
    except (InvalidOperation, ValueError):
        invalid_count += 1
        continue

    seen.add(key)
    cleaned.append({
        "symbol": row["symbol"],
        "date": row["date"],
        "close": str(price),
    })

# 3. Clean 데이터 저장
with open(data_dir / "clean.json", "w", encoding="utf-8") as f:
    json.dump(cleaned, f, ensure_ascii=False, indent=2)

print(f"원본: {len(raw_data)}건")
print(f"정제 완료: {len(cleaned)}건")
print(f"유효하지 않은 가격: {invalid_count}건")
```

터미널에서 프로젝트 폴더로 이동한 뒤 실행한다.

```powershell
python day01/pipeline.py
```

예상 실행 결과:

```text
원본: 4건
정제 완료: 2건
유효하지 않은 가격: 1건
```

실행 후 [data/raw.json](./data/raw.json)과 [data/clean.json](./data/clean.json)을 열어 비교해보자. 다시 실행하면 두 파일은 새 결과로 덮어쓴다.

### 코드를 쉽게 읽는 순서

| 코드 | 하는 일 |
| --- | --- |
| `Path(__file__).parent / "data"` | `pipeline.py`가 있는 폴더 아래의 `data` 폴더를 가리킴 |
| `mkdir(exist_ok=True)` | 폴더가 없으면 만들고, 이미 있으면 그대로 사용 |
| `with open(...)` | 파일을 열어 사용하고, 작업이 끝나면 자동으로 닫음 |
| `json.dump(...)` | Python 데이터를 JSON 파일에 씀 |
| `for row in raw_data` | 데이터를 하나씩 꺼내 확인 |
| `(row["symbol"], row["date"])` | 종목과 날짜를 묶어서 중복 확인 기준으로 사용 |
| `seen` | 사용하기로 한 종목·날짜 조합을 기록하는 곳 |
| `continue` | 현재 데이터를 건너뛰고 다음 데이터 확인 |
| `cleaned.append(...)` | 검사를 통과한 데이터를 결과 목록에 추가 |

`seen`은 같은 값을 중복해서 담지 않는 `set`이다. “이미 남긴 종목과 날짜를 적어두는 메모”라고 생각하면 된다.

`Decimal`은 소수점이 있는 수를 다루는 도구다. 일반적인 `float` 계산에서는 작은 소수 오차가 생길 수 있어, 이 예제는 가격 문자열을 `Decimal`로 바꿔 검사한다.

가격은 **숫자로 바꿀 수 있고, 0보다 크며, 무한대나 `NaN` 같은 특수한 값이 아니어야 한다.** 문제가 생기면 `except`에서 오류 개수를 늘리고 다음 데이터로 넘어간다. `try`와 `except`는 정해둔 오류가 발생했을 때의 처리 방법을 적는 문법이다.

JSON으로 저장할 때는 `str(price)`로 가격을 다시 문자열로 바꾼다. 그래서 `clean.json`에도 가격이 `"620.50"`처럼 보인다. 이 실습은 숫자 형식을 바꾸어 검사한 뒤 문자열로 보관하는 방식이며, 앞의 SQL 예시는 숫자 형식으로 변환하는 방식이다.

Python에서 값이 없다는 뜻인 `None`은 JSON 파일에 `null`로 저장된다. `ensure_ascii=False`는 한글 같은 문자가 그대로 보이게 하고, `indent=2`는 읽기 편하게 들여쓰기를 넣는다.

### 결과가 2건인 이유

| 처음 데이터 | 결과 | 이유 |
| --- | --- | --- |
| QQQ / 2026-10-26 / 620.50 | 남김 | 처음 나온 종목·날짜이고 가격도 정상 |
| SPY / 2026-10-26 / 680.20 | 남김 | 처음 나온 종목·날짜이고 가격도 정상 |
| QQQ / 2026-10-26 / 620.50 | 제외 | 같은 종목과 날짜를 이미 남겼음 |
| SPY / 2026-10-27 / `None` | 제외 | 사용할 가격이 없음 |

**원본 4건 = 남긴 데이터 2건 + 중복 1건 + 잘못된 가격 1건**이다. 현재 화면에는 중복 건수를 따로 출력하지 않는다.

처리 순서도 결과에 영향을 준다.

- 같은 종목과 날짜에 정상 가격이 여러 개면 처음 통과한 데이터만 남긴다.
- 잘못된 가격은 `seen`에 기록하지 않는다. 따라서 나중에 같은 종목·날짜의 정상 가격이 들어오면 남길 수 있다.
- 이미 남긴 종목·날짜라면 가격을 검사하기 전에 건너뛴다. 그 데이터의 가격이 잘못되어 있어도 `invalid_count`에는 포함되지 않는다.

이것은 학습용 코드다. 실제 서비스에서는 가격이 서로 다른 중복 데이터를 어떻게 처리할지, 오류 데이터를 어디에 보관할지 등의 규칙도 정해야 한다. 현재 코드는 날짜 형식이나 빈 종목명을 검사하지 않으며, 필요한 항목 자체가 빠져 있으면 실행이 중단될 수 있다.

### Step 3. 지금 코드는 ETL일까, ELT일까?

먼저 실제 흐름을 적어보자.

```text
코드에 적어둔 raw_data
    → raw.json에 원본 저장
    → Python에서 가격 검사와 중복 제거
    → clean.json에 결과 저장
```

원본을 보존한 뒤 변환하고, 변환한 결과를 별도로 저장하는 흐름이다. 다만 `raw.json`을 다시 읽거나 데이터베이스 안에서 변환하는 것은 아니다. Python이 코드 안의 `raw_data`를 직접 처리한다.

**Python에서 정리한 뒤 결과를 저장한다는 점에서는 ETL과 비슷하고, 원본을 먼저 저장한다는 특징도 함께 있다.** 이 예제를 전형적인 ELT라고 외우기보다, 어느 시점에 무엇을 저장하고 어디에서 변환하는지 이해하는 것이 중요하다.

나중에는 같은 작업을 PostgreSQL과 dbt로 구현하면서 차이를 비교한다.

`pipeline.py`의 `raw_data`를 한 번에 하나씩 바꾸고, 실행 전에 결과를 예상해보자.

1. 기존 데이터와 다른 종목이나 날짜에 정상 가격을 추가한다. 정제 결과가 3건으로 늘어나는지 확인한다.

같은 종목과 날짜에 가격이 `620.50`인 데이터와 `621.00`인 데이터가 들어왔다고 해보자.

- 현재 코드는 어떤 가격을 남길까?
- 두 데이터의 순서를 바꾸면 결과가 달라질까?
- 지금 방식으로는 왜 올바른 가격을 선택했다고 확신하기 어려울까?

```text

```

이 과제는 앞으로 배울 **데이터 품질, 중복 제거, 멱등성**과 연결된다. 멱등성은 같은 작업을 여러 번 실행해도 최종 결과가 한 번 실행했을 때와 같도록 만드는 성질이다. 예를 들어 저장에 실패해서 다시 실행하더라도 같은 데이터가 계속 추가되지 않게 하는 것이다.

오늘의 `seen`은 한 번 실행하는 동안의 중복을 막는 장치다. 프로그램을 다시 실행하면 새로 만들어진다. 오늘 예제는 같은 입력으로 파일을 덮어쓰지만, 나중에 데이터베이스에 추가로 저장할 때는 반복 실행에서도 중복을 막을 방법을 따로 마련해야 한다.
