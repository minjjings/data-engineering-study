# Day 99. 품질 검사 뒤 결과 공개하기

**20주 차 · 주간 4일차 | 약 90~120분**

[전체 계획](../README.md) · [120일 목차](../README.md#day-index) · [← Day 98](../day98/README.md) · [Day 100 →](../day100/README.md)

이번 주에는 **데이터 품질 규칙과 실패 처리** 내용을 다룬다. 오늘은 부분 결과를 분석 사용자가 읽지 않게 한다.

> 미리 작성한 교재다. 아래 예제·예상 결과는 학습 기준이며 실행을 완료했다는 뜻은 아니다. 과제에서 요구하는 코드·설정·결과는 직접 작성한다. 시장 가격은 가상 데이터다.

## 오늘의 학습 목표

- 부분 결과를 분석 사용자가 읽지 않게 한다.
- 예제의 입력과 결과를 비교하고 처리 기준을 자기 말로 설명한다.
- 직접 작성한 과제와 실행 근거를 남긴다.

| 순서 | 할 일 | 예상 시간 |
| --- | --- | --- |
| 1 | 개념과 준비 항목 확인 | 20분 |
| 2 | 예제 실행·입출력 확인 | 25~35분 |
| 3 | 직접 구현·실패 또는 경계 상황 실험 | 30~45분 |
| 4 | 결과 기록과 리뷰 | 15~20분 |

## 1장. 개념 이해하기

파일 생성과 공개를 분리하면 검증되지 않은 결과를 숨길 수 있다. DB에서는 staging 표를 검증한 뒤 트랜잭션으로 공개하고, 파일 레이크에서는 검증된 배치를 가리키는 manifest 같은 방법을 사용할 수 있다. 여러 S3 파일 이동이 자동으로 하나의 원자적 작업인 것은 아니다.

## 2장. 실습 준비

기존 Python 정제·PostgreSQL DW·dbt 프로젝트를 사용한다. 품질 오류는 별도 학습 배치에 넣고 Raw의 최초 샘플을 보존한다. 아래 SQL의 고정 CTE는 실제 운영 표를 변경하지 않는다. 코드·계약·규칙은 quality/ 아래에 정리한다.

이전 학습일의 과제를 아직 구현하지 않았다면 해당 교재에서 먼저 준비한다. 문서 안의 파일명은 앞으로 작성할 산출물을 포함한다. 첫 사용 환경은 이번 주 첫 교재인 [Day 96](../day96/README.md)의 준비 항목도 확인한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```json
{
  "batch_id": "2026-10-26-v1",
  "status": "validated",
  "data_prefix": "curated/market/batches/2026-10-26-v1/",
  "row_count": 4,
  "contract_version": 1
}
```

**예상 결과와 확인 기준:** 공개 manifest 설계 예시다. 검증 성공 이후에만 만들고 소비자가 해당 위치를 읽도록 구현해야 한다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. 저장 → 품질 검사 → 공개 순서를 Airflow DAG에 반영한다.
2. 검사 실패 배치가 기존 정상 결과를 덮어쓰지 않는지 확인한다.
3. DB 목표 표 변경과 공개 상태 갱신의 트랜잭션 경계를 기록한다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day99/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

YOUR_BUCKET 같은 예시 이름을 본인의 실습 환경 값으로 바꾼다. JSON 작성과 실제 서비스 적용·검증을 구분한다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
