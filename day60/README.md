## 1장. 개념 이해하기

S3는 원본과 정제 파일, Catalog는 정의, Athena는 S3 조회, DW는 분석 모델을 담당한다. Redshift는 DW 선택지이지만 이번 소규모 실험은 PostgreSQL로 검증한다. 새로운 도구는 필요한 규모와 운영 요구를 근거로 추가한다.

## 2장. 실습 준비

S3·Catalog·로컬 PostgreSQL을 사용한다. Glue Python shell 작업을 작은 JSON Lines로 한 번 실행한다. 실습용 역할에 입력·스크립트 읽기, 출력 prefix 쓰기, 로그 권한을 부여한다. Python 런타임·타임아웃·실행 용량을 기록한다. Redshift는 역할 비교까지 필수이며 생성은 선택 과제다.

이전 학습일의 과제를 아직 구현하지 않았다면 해당 교재에서 먼저 준비한다. 문서 안의 파일명은 앞으로 작성할 산출물을 포함한다. 첫 사용 환경은 이번 주 첫 교재인 [Day 56](../day56/README.md)의 준비 항목도 확인한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```text
Raw 4행 → S3 JSON Lines → Glue Python shell → 정상 키 2개
        → PostgreSQL DW → dbt mart
Athena + Catalog → S3 Raw의 경로·건수 확인
```

**예상 결과와 확인 기준:** 각 연결의 입력·출력·실행 기록을 보여준다. 설계 그림만으로 실행 완료를 판단하지 않는다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. PostgreSQL·Athena·Redshift의 사용 상황을 비교한다.
2. 10~12주 비용과 불필요한 Glue·Crawler 상태를 확인해 정리한다.
3. 유지할 Raw·Catalog와 나중에 재구축할 절차를 기록한다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day60/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

설계·검증 시나리오 예제는 실행 결과와 대응시켜 읽는다. 실행 명령으로 입력하지 않고 본인이 구현한 코드·로그·결과와 대응시킨다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
