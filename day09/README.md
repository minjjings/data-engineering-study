## 1장. 개념 이해하기

ROW_NUMBER는 묶음 안에 순번을 붙이면서 개별 행을 보존한다. 최신 시각이 같으면 결과를 결정할 추가 기준이 필요하다. id처럼 안정적인 보조 키를 넣어야 재실행 시 같은 행을 선택할 수 있다.

최신 원본을 먼저 고른 뒤 품질 검사하면 잘못된 최신 값이 있는 키는 제외된다. 정상 값만 남긴 뒤 최신을 고르면 이전 값을 사용할 수 있다. 둘 중 무엇이 맞는지는 수정·취소 데이터의 의미까지 고려해 정한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```sql
WITH raw(id, symbol, value, collected_at) AS (
    VALUES (1, 'QQQ', '620.50', TIMESTAMP '2026-10-28 10:00:00'),
           (2, 'QQQ', 'N/A', TIMESTAMP '2026-10-28 10:00:00')
), ranked AS (
    SELECT *, ROW_NUMBER() OVER (
        PARTITION BY symbol ORDER BY collected_at DESC, id DESC
    ) AS rn FROM raw
)
SELECT * FROM ranked WHERE rn = 1;
```

**예상 결과와 확인 기준:** id 2인 N/A가 선택된다. 최신 행 선택 자체는 가격 유효성을 보장하지 않는다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. 정상 가격을 먼저 고르는 정책과 최신 원본을 먼저 고르는 정책을 각각 SQL로 구현한다.
2. 동률 시 id 정렬을 빼면 왜 선택 결과를 보장할 수 없는지 설명한다.
3. 정책별 선택·제외 건수와 이전 값 사용 여부를 비교표로 만든다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day09/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

SQL 실행 위치를 확인한다. 일반 PostgreSQL SQL은 psql에서, Athena SQL은 Athena에서, Jinja가 있는 모델 SQL은 dbt 모델 파일에서 실행한다. TEMP 테이블은 생성한 연결에서만 보인다.
