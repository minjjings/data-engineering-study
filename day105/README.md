# Day 105. 장애 대응 문서와21주 리뷰

**21주 차 · 주간 5일차 | 약 90~120분**

[전체 계획](../README.md) · [120일 목차](../README.md#day-index) · [← Day 104](../day104/README.md) · [Day 106 →](../day106/README.md)

이번 주에는 **로그·지표·모니터링과 장애 대응** 내용을 다룬다. 오늘은 원인 확인부터 데이터 검증까지의 복구 절차를 남긴다.

> 미리 작성한 교재다. 아래 예제·예상 결과는 학습 기준이며 실행을 완료했다는 뜻은 아니다. 과제에서 요구하는 코드·설정·결과는 직접 작성한다. 시장 가격은 가상 데이터다.

## 오늘의 학습 목표

- 원인 확인부터 데이터 검증까지의 복구 절차를 남긴다.
- 예제의 입력과 결과를 비교하고 처리 기준을 자기 말로 설명한다.
- 직접 작성한 과제와 실행 근거를 남긴다.

| 순서 | 할 일 | 예상 시간 |
| --- | --- | --- |
| 1 | 개념과 준비 항목 확인 | 20분 |
| 2 | 예제 실행·입출력 확인 | 25~35분 |
| 3 | 직접 구현·실패 또는 경계 상황 실험 | 30~45분 |
| 4 | 결과 기록과 리뷰 | 15~20분 |

## 1장. 개념 이해하기

작업을 다시 시작했다고 데이터가 복구된 것은 아니다. 원본 존재·처리 상태·최종 키와 가격·최신성을 확인해야 한다. Runbook은 다음 사람이 같은 순서로 원인을 좁히고 안전한 재처리를 할 수 있게 쓴다.

## 2장. 실습 준비

로그는 기존 배치의 batch_id를 기준으로 연결한다. Day102에서 PostgreSQL ops_lab.pipeline_runs를 만들고 실행 지표를 저장한다. Day103에서 별도 Grafana 환경을 추가해 PostgreSQL을 조회한다. Prometheus 추가는 선택 과제로 두고 이번 주는 하나의 지표 저장 경로를 완성한다.

이전 학습일의 과제를 아직 구현하지 않았다면 해당 교재에서 먼저 준비한다. 문서 안의 파일명은 앞으로 작성할 산출물을 포함한다. 첫 사용 환경은 이번 주 첫 교재인 [Day 101](../day101/README.md)의 준비 항목도 확인한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```text
1. 영향 구간과 마지막 정상 batch_id 확인
2. Airflow Task 로그·DB 연결·원본 경로 확인
3. 실패 원인 수정, 공개되지 않은 배치 상태 확인
4. 해당 구간만 재실행
5. 키·건수·가격·품질 검사·최신성 대사
6. 경고 해제와 복구 시각·재발 방지 기록
```

**예상 결과와 확인 기준:** 재현한 장애1건에 대해 각 단계의 실제 명령·조회 결과를 채운다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. 배치 실패 또는Consumer lag 중 하나를 선택해 원인·영향을 재현한다.
2. 로그와 대시보드로 발견하고 Runbook만 따라 복구한다.
3. 지표 정의·경고 기준·대시보드·장애 타임라인을21주 산출물로 정리한다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day105/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

설계·검증 시나리오 예제는 실행 결과와 대응시켜 읽는다. 실행 명령으로 입력하지 않고 본인이 구현한 코드·로그·결과와 대응시킨다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
