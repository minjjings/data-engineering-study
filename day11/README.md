## 1장. 개념 이해하기

테이블의 grain은 한 행이 무엇을 의미하는지다. 오늘 가격 표는 종목 하나의 거래일 하루를 나타낸다. 자동 증가 id와 업무상 같은 데이터를 판별하는 키는 다르며 symbol·trade_date 조합에 유일성을 줄 수 있다.

PK는 행을 식별하고 FK는 참조 대상이 실제 존재하는지 검사한다. CHECK는 양수 같은 행 내부 규칙을 제한한다. 제약 조건은 애플리케이션 실수를 막지만 문자열 원본 보존을 위한 Raw에는 별도 설계가 필요하다.

## 2장. 실습 준비

Day 2 PostgreSQL을 사용한다. 학습용 테이블은 `lab_` 접두사나 TEMP로 구분하고 Raw는 수정하지 않는다. Day 14~15는 Day 11~12에서 설계한 키·트랜잭션을 확장한다. SQL은 `sql/week03/`에 기록한다.

이전 학습일의 과제를 아직 구현하지 않았다면 해당 교재에서 먼저 준비한다. 문서 안의 파일명은 앞으로 작성할 산출물을 포함한다. 첫 사용 환경은 이번 주 첫 교재인 [Day 11](../day11/README.md)의 준비 항목도 확인한다.

## 3장. 예제로 따라 해보기

먼저 예상 결과를 읽고 어떤 입력이 어떤 이유로 남는지 생각한다. 아래 코드가 부분 예제라면 주석에서 지정한 파일·함수·이전 코드에 합친다.

```sql
CREATE TEMP TABLE lab_symbols (symbol text PRIMARY KEY);
INSERT INTO lab_symbols VALUES ('QQQ'), ('SPY');
CREATE TEMP TABLE lab_prices (
    symbol text REFERENCES lab_symbols(symbol),
    trade_date date NOT NULL,
    close_price numeric(12,2) NOT NULL CHECK (close_price > 0),
    PRIMARY KEY (symbol, trade_date)
);
INSERT INTO lab_prices VALUES ('QQQ', '2026-10-26', 620.50);
SELECT * FROM lab_prices;
```

**예상 결과와 확인 기준:** QQQ 가격 1건이 저장된다. 같은 키 재삽입, 미등록 종목, 비양수 가격은 각각 제약 조건 오류를 내야 한다.

화면 출력이나 성공 상태만으로 끝내지 않고, 오늘 목표와 직접 연결되는 건수·키·값·상태를 확인한다.

## 4장. 직접 해볼 실습 과제

1. 같은 키·다른 가격을 삽입해 충돌을 확인하고 오류를 기록한다.
2. 미등록 종목·음수·NULL 가격을 각각 따로 입력해 실패 이유를 비교한다.
3. 실제 적재용 public.lab_symbols와 public.lab_prices DDL을 파일로 작성하고 ERD를 텍스트로 설명한다.

작성한 코드·SQL·설정은 이 day 폴더 또는 과제에서 지정한 공통 디렉터리에 저장한다. 실행 기록은 `day11/notes.md`에 남긴다. 원본 예제와 별도 경로를 사용하고, 오류 입력·재실행으로 결과가 달라졌다면 그 이유도 기록한다.

## 5장. 막혔을 때 확인하기

SQL 실행 위치를 확인한다. 일반 PostgreSQL SQL은 psql에서, Athena SQL은 Athena에서, Jinja가 있는 모델 SQL은 dbt 모델 파일에서 실행한다. TEMP 테이블은 생성한 연결에서만 보인다.

예상 건수와 다르면 사용한 입력·필터·기존 상태부터 비교한다. 해결하지 못한 오류는 입력과 실행 명령, 오류 메시지를 함께 남긴다.
